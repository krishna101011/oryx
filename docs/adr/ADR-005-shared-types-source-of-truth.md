# ADR-005 — TypeScript-First Contracts, Pydantic Mirror Generated

**Status:** Accepted
**Date:** 2026-06-06
**Phase introduced:** 1

## Context

Frontend is TypeScript. Backend is Python. They must agree on every payload. The standard answers all have failure modes:

- Hand-write types in both places — drifts within a sprint
- OpenAPI-first with codegen on both sides — backend leads, frontend follows blindly, contract changes hide in giant diffs
- Protobuf — heavy infrastructure for an HTTP/JSON product

## Decision

`packages/shared-types/` is the **source of truth**, written in TypeScript. A build script (`infra/scripts/gen-pydantic.ts`) converts each TS file into a matching pydantic model committed at `apps/backend/src/anant/shared/types.py`. CI runs `pnpm drift:check` on every PR; mismatch fails the build.

Frontend imports TS directly. Backend imports the generated pydantic mirror.

## Consequences

**Positive**

- A breaking contract change appears in the same PR as a diff on **both** sides
- Frontend devs write contracts in their native language
- OpenAPI remains the *external* contract (auto-generated by FastAPI for any third party)

**Negative**

- One direction only — Python developers can't extend a contract without TypeScript
- The generator is a custom script; one more thing to maintain

**Revisit when**

- We add a second backend service in a different language, or
- The hand-curated generator becomes a bottleneck (then replace with a proper AST-based one)

## Alternatives considered

- **OpenAPI-first codegen** — rejected; backend-led contracts feel backward for a product-led team
- **Hand-written both sides** — rejected; drift in week one
- **gRPC / Protobuf** — rejected; overkill for HTTP/JSON, painful in RN
